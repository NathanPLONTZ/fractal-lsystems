# Fractals and L-systems

2D modelling of plant-like shapes with Lindenmayer systems, and an experimental
measurement of their fractal dimension. Written in C++, with no dependency
beyond the standard library — the program writes its own BMP files.

## Context

This was a Master 1 research-introduction project (2023–2024) on the state of
the art in fractals. The assignment asked for a bibliographic study of the
field — the main definitions and mathematical properties, varied examples of
natural and synthetic fractal shapes, and a survey of generation algorithms —
followed by an implementation of one or more of those algorithms in C/C++, and,
for one implemented example, an experimental measurement of its
Hausdorff–Besicovitch dimension.

This repository is the implementation side of that work. It took the following
angle: use L-systems to grow plant-like structures, then measure how fractal
they actually are.

A fractal is a shape that shows detail at every scale. Formally, it is the
unique fixed point of a contracting transformation, so iterating a simple
geometric rule on a starting figure produces figures that grow ever more
intricate while keeping the same overall structure. The characteristic property
is a dimension that is generally **not an integer**.

An **L-system**, named after the biologist Aristid Lindenmayer, is a formal
grammar `{V, S, w, P}`: an alphabet `V`, a set of constants `S`, a start axiom
`w`, and a set of rewriting rules `P`. What distinguishes it from an ordinary
formal grammar is that **every symbol is rewritten at each step**, not just one.
Lindenmayer introduced them to model plant growth, which is why they produce
convincing vegetation.

The resulting word is drawn with the classical **turtle interpretation**, where
each symbol is an instruction:

| Symbol | Meaning |
|:---:|---|
| `F`, `X`, `Y` | move one step forward, drawing |
| `+` | turn right by the system's angle |
| `-` | turn left by the system's angle |
| `[` | save the current position and heading |
| `]` | restore the last saved position and heading |

`[` and `]` are what make branching possible, and therefore what make these
shapes look like plants.

## Data

There is no input dataset: every image is generated from a handful of
parameters. The only data files in the repository are the box-counting
measurements under `Lsystem/Test/`:

| File | Content |
|---|---|
| `dataXFlocon.txt`, `dataYFlocon.txt` | `log(s)` and `log(N)` for the Koch snowflake, 5 samples |
| `dataXRameau.txt`, `dataYRameau.txt` | `log(s)` and `log(N)` for the Branchlet L-system, 6 samples |
| `DimensionFractale.xlsx` | the same samples, with the regression plots |
| `regressionLineaire.R` | fits the slope of `log(N)` against `log(s)` |

These are regenerated by the `enregistrementData()` function in
`Fractales/FloconDeKoch.cpp` and `Lsystem/Test/TestLsystemRameau.cpp`; the call
is commented out in `main()` by default, because it redraws the shape at six
scales on a 4001×4001 canvas and takes a long time.

### Design notes

Two patterns carry the L-system engine.

**Rules are a chain of responsibility.** `Regles::resoudre` asks each rule in
turn whether it knows the symbol and passes it along if not. A symbol that no
rule claims is a constant and is copied through unchanged — which is exactly how
`+`, `-`, `[` and `]` survive rewriting without needing rules of their own.

**Drawing is a visitor.** `Symbole::action` is overloaded once per concrete
L-system, so a symbol can read and update that system's own turtle state. The
only thing that varies between systems is the turning convention, which each
system answers through its `rotation()` and `reinitialiseOrientation()`; the
turtle step itself is written once in `ActionsTortue.h`.

## Building and running

Requires a C++11 compiler and `make`. Developed with MinGW g++ on Windows; the
paths are platform-neutral, so it builds on Linux and macOS too.

```sh
cd Makefile
make                      # build all 17 programs
make FloconDeKoch.exe     # build just one
make run-FloconDeKoch     # build it and run it
make clean
```

If `g++` is not on your `PATH`, point at it:

```sh
make CXX="C:/MinGW/bin/g++"
```

Programs must be run from the `Makefile/` directory — they write into
`../Images/`, which `make` creates.

```sh
cd Makefile
./TestLsystemRameau.exe        # -> ../Images/LsystemRameau.bmp
./Mandelbrot_Julia.exe         # -> ../Images/Mandelbrot.bmp
./Mandelbrot_Julia.exe julia   # -> ../Images/Julia.bmp
```

Output is BMP, 32 bits per pixel. Note that the image is never held in memory:
`GrosseImage` seeks and writes one pixel at a time, which is what makes
3000×3000 canvases possible without allocating them, but also makes the larger
programs slow — the Koch snowflake takes several minutes.

To fit the dimension from the recorded samples:

```sh
cd Lsystem/Test
Rscript regressionLineaire.R
```

### Fractal dimension

The fractal dimension measures how a shape fills space across scales, and it is
what makes a fractal a fractal: it is generally not an integer. Intuitively, if
a shape has dimension `D`, its measure is multiplied by `n^D` when its size is
multiplied by `n`. A segment doubles in length when doubled in size, so `D = 1`;
an area quadruples, so `D = 2`.

The **Hausdorff–Besicovitch** dimension is the rigorous definition, but it is
hard to apply. The **Minkowski–Bouligand** dimension, or *box counting*, is the
practical one and is what this project uses. The method lays a grid over the
shape and counts the cells it touches, then repeats with the grid reduced by a
scale factor `s`. With `N` the number of cells covered:

```
N ≈ c · s^D        ⟹        log(N) ≈ log(c) + D · log(s)
```

so `D` is the slope of `log(N)` against `log(s)`, obtained by linear regression.
Here one pixel is one box, so counting boxes means counting non-background
pixels (`BoxCounting.h`).

The method was first checked on the **Koch snowflake**, whose dimension is known
analytically to be `log(4)/log(3) ≈ 1.2619`, before being trusted on an original
shape.

| `log(s)` | `log(N)` |
|---:|---:|
| 0 | 4.61512 |
| 0.693147 | 5.86079 |
| 1.38629 | 6.73934 |
| 2.07944 | 7.46221 |
| 2.77259 | 8.18396 |

> **Measured dimension: 1.2608** (R² = 0.985), against a true value of 1.2619 —
> an error of about 0.1%.

Only then was it applied to the **Branchlet**. This one is not a reproduction of
anything: it is an L-system invented for this project, so there is no published
value to check the answer against — which is exactly why the method had to be
validated on the snowflake first.

| `log(s)` | `log(N)` |
|---:|---:|
| 0 | 7.92949 |
| 0.693147 | 8.93485 |
| 1.38629 | 9.74771 |
| 2.07944 | 10.5272 |
| 2.77259 | 11.2627 |
| 3.46574 | 11.9929 |

> **Measured dimension: 1.1575** (R² = 0.997)

A dimension of 1.1575 against the snowflake's 1.2608 is consistent with what the
two images show: the Branchlet is a set of lines reaching into space, while the
snowflake's boundary crinkles enough to start filling the plane. The more
irregular and fragmented the shape, the higher its dimension.

Both figures sit strictly between 1 and 2 — neither a curve nor a surface —
which is the defining signature of a fractal object.

### Reproducibility

The refactoring of this codebase was validated by rendering every program before
and after and comparing the output bitmaps byte for byte. The results, including
the two programs that are not reproducible by construction, are recorded in

## Limitations and possible extensions

- **No colour or shading.** Every shape is drawn in a single colour. Real
  plants need per-part colouring and light, which the turtle interpretation can
  support through terminal symbols carrying a colour.
- **No real-time view.** Images are written to disk, so changing a parameter
  means a full re-render. Driving the same engine from a game engine would make
  parameter exploration interactive.
- **Only the turtle interpretation.** It is used universally for L-systems, but
  it is a choice, not a necessity; other interpretations of the same grammars
  are unexplored.
- **Two dimensions only.** The grammars extend naturally to 3D through the
  pitch and roll symbols (`&`, `^`, `<`, `>`), which are defined in the
  literature but not implemented here.
- **`GrosseImage` is slow by design.** One seek, one write and one flush per
  pixel. Buffering a row at a time would speed the large renders up by orders
  of magnitude without changing a single output byte.
